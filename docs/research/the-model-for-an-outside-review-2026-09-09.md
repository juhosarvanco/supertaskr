# My model for software development with AI — for an outside review

Written 2026-09-09 to answer three questions from a reviewer: the workflow steps, the setup, and the main friction points. Everything below describes the system as it ran last night on its own repository (the method builds itself). Figures are measured, not estimated; each says where it comes from.

The model is called Supertaskr. Its one-sentence claim: a product idea becomes a thoroughly planned board of exact, dispatchable tasks, then a governed loop of AI agents builds, verifies and merges those tasks, with the project folder as the complete, successor-proof record of everything decided, built, checked and why. The principle underneath it: **the better the builder models get, the more the bottleneck is knowing what to build and proving it was built** — so the interview and the verification carry the weight, and the code is the cheap part.

---

## 1. The workflow steps — from an idea or a bug report to merged code

The unit of work is a **card**: one markdown file with machine-read frontmatter (id, size S/M/L, priority, status, `touches:` — the files it may change — builder, verifier) and acceptance criteria in EARS form ("WHEN … THE system SHALL …"), written so that each criterion can be held by a test. A bug report, a verifier's finding, a human idea — all enter as a card with `status: suggested`. Nothing is done that is not a card.

**Step 0 — Genesis (once per project).** A seven-question interview, one question at a time, each answer banked to disk as it is confirmed: the problem and the person, what success measurably means, the non-goals, the constraints, the stack and why, the riskiest assumption, the smallest first slice. It ends with five governing documents (north star, roadmap, architecture, conventions, state) and the first board. The interview challenges weak answers instead of transcribing them.

**Step 1 — Triage.** A human (me, in the architect's seat) or the seat on the human's standing instruction promotes suggested cards to `planned` with a priority, a size and a fence (`touches:`). Product decisions are the human's only; the AI seat never takes one. Open questions go to "rooms" (a file per question); decisions become ADRs.

**Step 2 — Dispatch, one command.** `brief.mjs --dispatch --full` DERIVES what is startable: planned cards with no unmet blocker whose fence is disjoint from every live lane's fence (computed over expanded paths, never eyeballed). Then one command, "the arm", does eight steps and refuses at the first that fails: stamp the card `building` (a commit), cut a git worktree on a branch named for the card, run a **preflight** over the card (every path the criteria name exists, every figure the card states re-derives, no unresolvable fence token, no prose the tooling misreads), write the fence manifest into the lane, cut a second detached worktree for the verifier ("the bench"), assemble the **brief**, and prove the lane's port is free. The brief is program-assembled, not chatted: the card, the fence, the ports, the base commit, the build order, the relevant conventions quoted by heading. It is about 38–40 KB.

**Step 3 — Build (the executor seat).** One spawned agent session (Claude Opus today) holds the executor role for one card, then ends. It reads the brief and the standing documents, builds inside the fence (a hook makes every file outside the fence read-only at the moment of the write), commits on the lane branch with messages that say what moved and why, and for every test body it adds it **drills a mutant**: plant a defect on the producer side, the body must go red alone, restore the site and prove the restore by hash. A positive control has to be shown failing against an implementation that lacks the property before it is trusted. It runs the suites its fence owes (a rule scopes which of the four suites a lane must run), writes a report file (tip commit, files moved, measurements, suite counts beside exits, mutants drilled, what it could not measure, new suggested cards), stamps the card `verifying`, then polls a file for the verdict. If it needs a file outside its fence it writes an "ask" file and keeps building; the seat answers in the same file. The lane cannot widen its own fence.

**Step 4 — Blind verification (two spawns).** The guarantee is informational blindness, not model diversity: the failure a builder cannot catch is a shared assumption, and assumptions travel through reasoning, not weights.
- *Phase 1* is a spawn given the card at its base commit and the verifier's role file pasted in, told to use no tools, and asked for an **attack set**: per criterion, a way to satisfy its letter while failing its purpose and the check that would catch it; the mutants it wants planted; the ground truths it wants measured at the base before the diff exists; what would falsify the work outright. The dispatcher saves it and hashes it, takes the requested ground truths at the base and hashes those too.
- *Phase 2* is a fresh spawn on the bench, checked out at the lane's tip, given only the two hashes, the tip, the base, the fence and the port. It verifies the hashes, reads the card at the base, reads the diff, runs every attack, plants its own producer-side mutants and reads their landing from `git diff`, runs the whole four-suite battery once at its tip, runs a mandatory security sweep, and only THEN opens the executor's report to re-derive every claim in it. It appends a verdict to the card: APPROVED, APPROVED WITH ASSIGNED CORRECTIONS (each correction named with the test body that pins it, which the verifier has run both ways), or REJECTED with reproducible commands. Improvement ideas become new suggested cards, never verdict text.
- A rejection re-enters as a fix pass by the executor in place, then a NEW phase 2 spawn; carried findings are re-judged by blob hash, only the refuted claims are re-run.

**Step 5 — Landing (the integrator, which is the architect seat).** Move the lane branch to the verdict commit, merge `--no-ff --no-commit`, stamp the card `done` with who built and who verified, regenerate the behaviour census (generated from the end-to-end test names, so a sentence in it is false the moment its test fails), regenerate the architecture graph if any indexed source moved and re-check the app's dogfood pins, run the docs gate (prose that a test reads is a code input). Then perform the verifier's assigned corrections to lane standards — each with its mutant drilled red alone and the restore proved — and commit once with a message that names everything the merge carries. Then the **four-suite battery is run LAST on the exact tree** (parser, app, Rust workspace, end-to-end) through one runner that writes a verdict token keyed to the tree the suites started on. The push goes through a guard that refuses a stale or unkeyed token, refuses while a CI run is in flight, and reports a merge unjudged if its lane branch is already gone. CI (one GitHub Actions job, pinned to the local runner by a parity test) is read after every push; a red there is attributed by name and filed as a card.

**Step 6 — Record.** Every sitting ends in a checkpoint: an append-only record (what merged, what the gates said, what the brief got wrong, the ADR-020 metrics: rework cycles, tokens per seat, gate runtime, cold-start cost, drift incidents) and the state file replaced from a template in the same commit, so a cold session resumes from disk. Health bands (suite seconds, the suggestion backlog and its age, the governing documents' byte headroom) are read at every checkpoint; a breach becomes a card. Records are never rewritten.

**Step 7 — Metabolism.** Every finding from steps 3–6 — a verifier's non-blocking observation, a gate that fired for a reason the tree does not carry, a wrong figure on a card — is filed as a suggested card and goes back to step 1.

Last night, on the method's own repository, this loop merged nine cards across two sittings (sizes S to L), with one rejection-and-fix cycle, one repair commit on main, and CI green on every push after a runner-disk problem was diagnosed and fixed by one of the cards.

## 2. The setup

**Interface.** I work in the Claude desktop app (Claude Code) with my project folder open. My session is the architect: it triages, dispatches, answers asks, folds verdicts, performs corrections, merges, runs batteries, pushes, watches CI and writes checkpoints. It spawns the other seats as background subagents through the app's Agent tool. No Cursor, no Copilot; the AI writes all of the code, I read verdicts and rule on decisions. A desktop "mirror" app (Tauri) sits beside the chat and renders the board, the lanes, the architecture map and the health bands from the files on disk; it writes nothing and spawns nothing.

**Models.** The architect session runs on Claude's top model. Executors and both verifier phases run on Claude Opus. A rule to run fix passes on Sonnet exists and has not been exercised yet. Phase 1 (the tool-less attack set) is the obvious place for a cheaper model and still runs on Opus.

**Multi-agent, file-based.** Agents cannot message each other in this harness, so every channel is a file in a scratch directory: the brief, the report, the verdict, the ask, the attack set and its ground truths (hashed). The architect arms shell watchers that poll for those files. A subagent cannot read its own token meter; it exists only in the completion notification the architect receives.

**Isolation.** One git worktree per lane and a second detached worktree per bench, all on one Mac. Each lane gets its own dev-server port derived from the card number. Suites that cannot share a machine (the Rust and end-to-end legs) take a per-checkout solo lock; the others run concurrently.

**The tooling is the product's own, and it is tested.** Everything above — the arm, the preflight, the fence hook, the brief assembler, the gate runner, the verdict token, the push guard, the docs gate, the health bands, the census generator — is a script or a hook in the repository, covered by the end-to-end suite (about 740 test bodies), and changed only through the same loop. The method itself (role contracts, the lane protocol, the task format, the interview, templates) is a versioned kit (v0.1.11 as of last night) that a new project copies in whole at genesis; a version bump is a three-file commit with a pin test that refuses a half-bump.

**Context handling.** Nothing is pasted by hand. A seat's standing read is its card plus the state, architecture and conventions documents — about 150 KB before its own files, three quarters of it the conventions — plus the ~40 KB brief. Verifiers read the card at the base commit and the diff, never the builder's reasoning. The architect's own context is the expensive one: it holds the whole night, compacts several times per sitting, and re-reads its ledger after each compaction.

## 3. The main friction points, measured

Numbers below come from last night's completion notifications and battery logs (2026-09-09, the method's own repository, sizes S to L).

**Tokens per card are dominated by verification and reading, not by writing code.**
- Executor seat, one card: 280k–350k tokens (four lanes measured: 282k, 309k, 335k+339k for one lane that needed a continuation, 346k).
- Verifier phase 2, one card: 250k–360k tokens (291k, 320k, 362k).
- Verifier phase 1 (tool-less attack set): 56k–65k tokens.
- So an S or M card costs roughly 0.6–0.8 million tokens end to end, excluding the architect's own context. The architect's cost is not derivable from inside the session; it is the largest single consumer because it carries everything.
- The standing read is 150 KB per seat, re-read at every compaction and by phase 2. A card in flight (T-254, "the context pack") replaces the whole conventions document with the bullets the card's gates actually cite, derived from the gates' own citations — the saving is unmeasured until it lands, and the card demands the measurement.

**Wall time per card is dominated by verification and by gates, in sequence.** A small card takes about 1.5–2.5 hours from dispatch to a pushed merge: build 40–60 min, verify 45–60 min, corrections at the merge 20–30 min, the four-suite battery 13–23 min (the end-to-end leg alone is about 12 min), CI 26 min. The end-to-end leg is a health band that breaches by a factor of five against the band set when the suite was a third of its size.

**Every push owes a full battery, and every commit on the integration branch invalidates it.** A docs-only commit, a dispatch stamp, a card promotion — each stales the verdict token, and the next push owes another 15–20 minutes of suites. Last night ran about a dozen batteries in nine hours, roughly 3.5 machine-hours, and twice two batteries collided on the solo lock. The remedy on the board is batching commits before a battery, which fights the loop's own cadence.

**Assigned corrections cost the architect more than the merge does.** Nearly every APPROVED verdict comes with two to four corrections the verifier has already written and demonstrated in its own transcript. The integrator has to perform them to lane standards (body, mutant drilled red alone, restore proved by hash), which means recovering the verifier's bodies from its transcript file or rewriting them. That is 20–30 minutes of the top model's attention per merge. The obvious fix — the verifier commits its correction bodies on the bench and the integrator only re-drills — is not ruled yet.

**The metabolism files more work than it closes.** The night filed 27+ suggested cards from seven lanes; the suggestion backlog is 67 against a health band that breaches at 40. Each verifier and each executor is required to file what it found; the triage cost lands on the human.

**Harness limits shape the method.** Agents cannot deny themselves tools, so phase 1's blindness is kept by instruction and every verdict discloses that. Agents cannot message each other, so the ask channel is a polled file, and a subagent that finishes while its own background job runs re-fires. The desktop app's safety classifier refuses a `kill` even of the session's own stale process, so a stuck suite has to be waited out. A usage limit killed five agents at once mid-night; they were re-spawned from their files, which is what the file-based design is for, and it cost about an hour.

**Prose is a code input, which is right and expensive.** The preflight reads cards strictly — an arrow character in a quoted paragraph, or a package named by its path in a criterion, refused two dispatches last night until the card was respelled. A test that derived a verb set from the whole text of two cards went red the moment a verdict was written onto one of them. The governing documents have byte budgets, so every sentence added owes a cut.

**The human's decisions are the real gate, and they queue.** Anything that is a product decision waits for me: a directory name, a UX direction, a naming ruling. The seat runs unattended overnight only on cards that need no decision, and it says so at every step.

**Where I want the review to push.** Which of these costs a professional team would refuse to pay (two verifier spawns per card? a full battery per push? corrections performed by the integrator?), which they pay differently (CI as the only gate? a shared context store instead of a 150 KB read per seat?), and where token spend could be cut without giving up the two properties the model exists for: a verifier that could not see the builder's reasoning, and a repository that is the complete record.
