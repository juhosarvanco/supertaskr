`triageClusters`' own doc comment records that the FIRST build keyed the
fence half on the connected components of *shares ground with*, that it
returned 75 of 80 live suggestions as one cluster, and that *"a cluster
that holds everything names nothing"*. The shipped build keys on the
GROUND instead and is genuinely better — 43 clusters where there was
one. **The dilution is not gone, though; it is smaller.** Driven against
the live board at `bf22ede`, the largest row is:

    T-153-s17, T-153-s18, T-203-s3 … T-282-s1 — all reserve tools/

**52 members of the 83 live suggestions, 63% of the column, on the bare
token `tools/`**; the second row is 38 members on `tools/e2e`. Both rows
are literally TRUE — every member does reserve that path — and both are
the sentence the comment refuses, because a triage seat cannot act on a
row naming 52 cards. The mechanism is a handful of cards fencing a broad
token: `T-264-s3` alone appears in more than thirty of the 43 clusters.

Nothing in the six new bodies can see this. They drive a 11-card fixture
where every fence is narrow, and the one live-board body asserts SHAPE
(every named id is a live suggestion; every suggestion is clustered or
counted alone) rather than USEFULNESS, so a view that put every card in
one row would satisfy it.

Two shapes worth weighing, and the measurement should pick: suppress a
cluster whose membership exceeds some fraction of the column and report
it as a COUNT with its token (the same move `alone` and `unfenced`
already make), or rank rows by specificity and spell only the narrowest
ground each pair shares. Either way the property wants a body driven off
a fixture where one card fences a broad token — which is the case the
current fixture has no member for.

Class parent: T-282. Disposition hint: promote behind T-282-s1 — the
view has to render before its readability is worth tuning.
