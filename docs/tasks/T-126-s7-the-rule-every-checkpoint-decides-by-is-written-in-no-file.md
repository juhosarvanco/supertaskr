## Why it is worth writing rather than leaving to each hand

It is the only rule that answers the question every integrator actually
faces — *this thing is wrong, is it mine?* — and the two wrong answers
are asymmetric. Repairing what the merge merely REVEALS silently expands
an unreviewed commit and hides a defect's age; filing what the merge
INTRODUCES ships a tree whose docs are false the moment they land, which
is the state `integrator.md`'s opening line ("leave the docs true")
exists to forbid.

## And it needs a second clause, which this merge is the evidence for

The bare rule is not sufficient, and a session applying it literally here
would have got it wrong. C-15's `paths:` entry and its module header were
both made false BY this merge, so the rule's first half reaches them —
yet repairing them was still the wrong call, because:

1. removing the `paths:` entry discharges **`T-033-s8`**, an open
   question addressed to the architect, **by side effect**; and
2. it fires T-024's three-fixture rule (`smoke.test.ts`,
   `architecture-dogfood.test.ts`, `map-dogfood-render.test.tsx`), which
   is a coordinated change with a real test surface — a card's work, not
   a checkpoint aside.

So the clause the rule wants is something like: **repair statements of
FACT; route anything whose repair would settle an open question or move a
pinned fixture set.** Both halves were needed to decide this merge, and
only the first half exists even orally.

## A third consideration, recorded because it is easy to argue the other way

Where the falsehood is the visible COST of a ruled violation, erasing it
in the same breath as ratifying the violation is how "ratified by
necessity, **not precedent**" quietly becomes precedent. That is a reason
to route rather than repair which has nothing to do with fences or
fixtures, and it will not occur to a reader of the bare one-liner.
