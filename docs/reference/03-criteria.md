# 03 — Criteria

Acceptance criteria are the contract a card is built to and attacked
against. They are written in EARS notation, one line per enforceable
check, and everything the verifier can prove is bounded by what they
say. This chapter is the notation, the rules a criterion must obey in
this method, and the additions ruled on 2026-09-08 from the
EARS-for-the-AI-era reading (docs/rooms/version-planning.md, third
sitting).

## EARS: the five patterns

The de facto standard for requirements that are unambiguous to humans
and to models (method/interview/decomposition.md step 3):

| pattern | form |
|---|---|
| Ubiquitous | THE system SHALL <behaviour> |
| Event-driven | WHEN <trigger> THE system SHALL <behaviour> |
| State-driven | WHILE <state> THE system SHALL <behaviour> |
| Unwanted behaviour | IF <failure or abuse> THEN THE system SHALL <response> |
| Optional feature | WHERE <feature enabled> THE system SHALL <behaviour> |

Every criterion maps about one-to-one onto a test case, written so the
verifier can enforce it mechanically with the commands in
docs/CONVENTIONS.md. Every card carries at least one IF/THEN line: the
edge cases live there. Ban words: fast, clean, robust, proper, good.
Each is converted to a number or an observable event, or deleted.

## The rules a criterion must obey

These are the method's own additions to EARS, each bought with an
incident recorded beside the rule in method/tasks/TASK-FORMAT.md and
method/interview/decomposition.md.

- **A criterion names the gate's command, never its output.** Write
  *"the gate SHALL report no unaccounted readers"* or the command
  itself; never *"the gate SHALL name five readers"*. A count is a fact
  about the tree at the moment the card was written and goes stale in
  the queue. If the number matters, the criterion says derive it and
  report it.
- **A criterion may not order work outside its own card's `touches:`.**
  A card whose criterion and fence disagree is a defective card. Either
  widen the fence before dispatch, or write the criterion as a route:
  *IF this path is outside the fence THEN record it, route it as a
  suggestion naming the fence it needs, and say so.*
- **A criterion can specify a check that cannot fail, and it reads
  exactly like a real one.** The shape: a relation between a policy and
  a view derived from that policy is a tautology. A coverage floor over
  "the tracked set minus the exclusions" deletes its own failure when an
  exclusion is added. Before a criterion ships, name the input that
  makes it fail; if you cannot, re-anchor one side to something the
  policy does not derive: a literal, a frozen fixture, an independently
  measured expectation. Gather the evidence by mutating the check, not
  the thing it checks.
- **Two criteria on one card can contradict each other.** The
  decomposition self-review reads the set against itself, not only
  against the tree.
- **A criterion demanding a test body needs a fence that can hold
  one.** The dispatch order classes a card UNFENCEABLE when its criteria
  ask for a spec and its `touches:` names no test path (T-225-s11's
  body; T-225-s20 files the remaining case).
- **A criterion is checkable at the moment it is read.** A transcribed
  measurement is checkable only against a tree that has moved.

## How the pipeline reads criteria

- **The executor** builds to them and reports each one: met and how, or
  NOT built and routed, naming the fence or room it needs.
- **The verifier** attacks every criterion literally, then the malformed
  inputs, boundaries and unhappy paths the criteria imply but do not
  spell out. Phase 1's floor is one attack per criterion, each naming a
  way to satisfy the letter while failing the purpose (chapter 07).
- **The docs gate** reads the card's structure; **the card preflight**
  reads the paths and figures the criteria name (chapter 10).
- **The census** (docs/CAPABILITIES.md) is the criteria's landed form:
  the e2e test names, one sentence each, regenerated by a program.

## EARS for the AI era: what was ruled in

The v2 reading (2026-09-08) starts from the observation that a model's
failure mode on an ambiguous sentence is to resolve it silently, where
a human's was to ask or stall. The additions move the human's decision
to the level of choices rather than sentences and make omission
visible. Each item below names its card and its version.

### The edge and must-not questions (v1, planned: T-253)

Decomposition asks two more questions per card: what are its edges
(boundary, adjacency, encoding, ordering), and what must it never do.
The kept answers are written as criteria: IF/THEN lines for the edges,
ubiquitous SHALL NOT lines for the prohibitions. This is where the
"and not otherwise" half of a requirement gets written down.

### The decision list (v1, folded into T-253)

Decomposition writes each card's decisions out: the question, the
options, the planner's proposed default, only for what the interview
and CONVENTIONS do not settle. A model that would have resolved the
ambiguity silently now leaves a list a human can read in a minute.

### Two decision modes, audit and auto (v1, planned: T-257)

A card carries `decide: audit` or `decide: auto`. Under audit the
preflight refuses an unanswered item and the human's name goes on the
choices. Under auto the planner's proposed default stands, stamped as
the planner's, and the record shows which mode ran. The mode is the
project's default in nputer.yaml and a card may override it.

### A test named per SHALL clause (v1, planned: T-252)

Each SHALL clause names, in a `proves:` note, the suite that will prove
it. The preflight lists the clauses that name none, advisory first.
The verifier's reach is bounded by the spec's reach; this makes the
bound visible before any code is written.

### The oracle class and the escalation form (v1, planned: T-259)

Each `proves:` note may carry an oracle class: proof, type, property or
example, strongest first. An example-only class on an "in every
state" or "and no other recovery" clause is a preflight finding,
because one example proves one path. The escalation pattern is the
sixth EARS form written for agents that decide when to stop:
*If <condition>, then the <agent> shall halt <action>, hand off to
<role> with <context>, and shall not proceed until <decision event>.*
nputer's rooms and stop rules already behave this way; T-259 gives the
form a place on the card.

### The commission list as a verifier rule (v1, planned: T-258)

Phase 2 enumerates every observable side effect the diff adds (I/O,
network, log lines, persistence, emitted events, scheduled work,
dependencies) and maps each to a criterion. An unmapped side effect is
a finding. The fence bounds paths; this bounds behaviour.

### Ruled to v2 and v3+

Catalogue-generated negatives, the "and not otherwise" tests generated
from the component registry, go to v2's productization pass once the
registry is complete enough. The weekly regeneration job, a fresh
agent rebuilding the implementation from sentences and glossary alone,
is v3+ under the eval corpus.

### Already delivered under other names

Test-writer independence is the blind verifier, inverted: the attack
set is written from the spec before the diff exists. Coverage per
requirement is the census. The glossary bound to symbols is the
component registry's slug map and the token lint's vocabulary check.
