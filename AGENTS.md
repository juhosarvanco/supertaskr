# supertaskr

## Development workflow (owner authorization, 2026-10-29)

Develop this product with native Codex tools, ordinary Git branches and
worktrees, focused tests, independent code review and CI. This replaces
the project's custom dispatch, grant, admission, binding, bench,
collection and merge ceremony for Supertaskr's own development. Those
capabilities remain product requirements; preserve their implementation,
tests and historical evidence. Do not retry or reroute previously
safety-blocked work or invent completion of unfinished proofs.

Keep migration drafts and the migration checklist in the existing sibling
supertaskr-evidence home until the permanent private records home works.
Ordinary private edits must not trigger product checks or publication.
Use GPT-6.1 Sol at extra-high effort for implementation and independent
review, with separate workspaces and clear ownership for parallel work.

The optional product hook configuration is preserved at
`.codex/supertaskr-product-hooks.json`; `.codex/hooks.json` deliberately
installs no custom development ceremony. Preserve platform restrictions.
The rules below apply where compatible with this authorization.

The project-genesis and multi-session development system — being built
with its own method (ADR-001).

Before product development, read CONTRIBUTING.md. It owns this source
checkout's setup, check and ordinary test commands. Confirm your task in
one paragraph before editing.

For work that explicitly selects a private project context, resolve that
context through the delivered binding contract first. Its private
`docs/STATE.md` and `docs/INDEX.md` are that task's standing read. Missing or invalid selected
records must be reported; never fall back to stale product docs. During
the migration, keep private drafts and the checklist in the existing
sibling evidence home as authorized above. Product-only contributions
require no private records, binding, credentials or remote.

For selected project work, follow its role file where it differs from the
shared read instructions: where the two differ, the role file wins.
Project tasks, decisions and rooms live in its selected records context.
If a project instruction conflicts with that project's north star, report
the conflict there. Product-only work uses the public contributor contract.
